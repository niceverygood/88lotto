# 88 추천 발급 원자 선점 배포 준비

이 문서는 코드 준비 절차이며 운영 반영·실제 문자 수신 완료 보고가 아니다.

## 배포 순서와 구분

1. 88 Git 저장소, Supabase 프로젝트, Vercel 프로젝트와 SMS 계정이 Plus와 별개임을 확인한다. 원본 작업 디렉터리의 변경을 덮어쓰지 않는다.
2. 88 스키마에서 members/staff/site_settings/sms_sends의 사용 컬럼과 source_site 분포를 읽기 전용으로 확인한다. 이 마이그레이션은 별도 이관을 실행하거나 회원 보류를 해제하지 않는다.
3. 현재 스키마 및 영향 대상 설정을 백업하고 88 전용 `20261005103000_atomic_reco_issue.sql`을 적용한다. 실발송 크론과 겹치지 않는 변경 창을 사용하며 구버전 웹 탭은 새로고침한다.
4. 새 API/UI를 같은 88 프로젝트로 배포한다. 인증 오류, rep의 다른 담당 회원 거부, leader 전체 범위와 read-only dryRun을 확인한다. Plus의 이관 시험 명단을 여기에 사용하지 않는다.
5. 실제 문자는 명확한 대상·기존 발송 여부·당일 구전산/신전산 운용 합의가 확인된 별도 승인 범위에서만 요청한다. 업체 접수와 실제 수신은 별도로 대조한다.

## 요청 규칙

- GET cron 및 audit 파라미터는 기존 일정대로 운용한다. `GET ?dryRun=1`은 쓰기 없이 적격 수를 조회한다.
- POST scheduled는 정확한 memberIds 1~50개, expectedRound 및 dryRun을 사용할 수 있다. manual은 회원 1명이고 setCount는 지정 시 1~100이다. 날짜·회차 생성은 서버와 DB가 재검증한다.
- 명시한 회원이 누락되거나 비활성이면 전체 대상으로 확대하지 않는다. 같은 회차의 원장 또는 발급 이력이 있으면 다시 발급하지 않는다.
- generation-only 발급도 원장을 차지한다. 이후 같은 회차의 문자를 자동으로 추가 발송하는 기능은 없다. 미발송 원인을 먼저 대조해야 한다.

## 장애와 복구

- claimed/unknown/rejected 및 접수 저장 실패는 재전송 대기열이 아니다. 같은 요청을 반복하지 않고 원장, 회원 문자내역, 업체 전송내역을 대조한다.
- 업체가 접수했더라도 DB 결과 응답이 유실될 수 있으므로 HTTP 실패만으로 미접수를 판단하지 않는다. UI에서도 401/네트워크 오류를 자동 재호출하지 않는다.
- 원장 테이블을 삭제하거나 기존 회원 발급 이력을 삭제하여 우회하지 않는다. 배포 후 장애 시 먼저 발송 진입점을 통제하고 안전장치를 유지한 전진 수정 또는 검증된 안전 버전을 사용한다.

## 검증 한계

로컬 API/UI 회귀와 합성 PostgreSQL 테스트는 운영 권한·등록 발신번호·업체 접수·실수신을 대체하지 않는다. 88 전용 운영 검증 결과는 비공개 인계 폴더에 따로 보존한다.
